# 在真实案例中共同演进

## 什么时候讨论

首次处理实际材料、首次处理不同性质的材料、用户提出不适用或输出暴露具体问题时，启动一次小范围讨论。已经确认且适用的规则直接沿用；不要求每次入库重选模板，不为迭代次数制造变更。

## 用什么讨论

先阅读当前材料和相关已有页面；读取库内 `Schema.md`（若存在）及与本案例相关的迭代记录，避免全量回读历史。没有确认记录时，将既有助手模板视为候选，不把“文件已存在”当用户认可。

展示足够判断的实际产物：代表性页面草稿、拟新建/复用节点及理由、关系链接和索引条目。篇幅随案例决定，优先小表格或关系图；未确认的内容放在对话或明确的草稿位置，不假装已整合进正式知识网络。

只问本次会改变结果的问题，例如：
- 这份材料最值得保留的是论证过程、概念机制还是行动步骤？
- 这个概念值得独立成页，还是保留在主题页更好找？
- 当前摘要遗漏了哪些以后会用到的细节？

给出推荐和具体影响，让用户评议实际样例。已有答案不重复问；用户允许试做时，可以用可恢复的局部方案试验并报告效果，但试用不等于永久生效。

## 讨论如何变成持久规则

| 内容 | 保存位置 | 生效条件 |
| --- | --- | --- |
| 尚未确认的建议 | 相关案例记录，标记“提议” | 不作为以后强制规则 |
| 本次特殊选择 | 相关来源页/案例记录 | 本案例授权，不扩大范围 |
| 本库通用约定 | 库内 `Schema.md` | 用户确认适用范围后写入 |
| 跨案例复用的方法 | Skill 的相关参考文件 | 有案例依据，用户认可推广；不升级为机器全局规则 |

首次有具体 Schema 决定时按需建立 `规则迭代记录.md`，以短条目记录：日期/规则ID、关联案例、发现的问题、提案、用户反馈依据、适用范围、状态、改动文件、验证结果和替代关系。状态区分“提议”“试用”“已确认”“已替代/撤回”；用户确认与实际效果验证分开记录，不虚构评价。

`Schema.md` 是模式文件，管理本库结构、约定及入库/查询/维护流程。原件不变、Wiki提炼关联、Schema指导维护是三层职责；材料中的简历方法等领域知识属于 Wiki，不能直接变成代理执行规则。页面模板文件 `page-schema.md` 是候选页面规范，不等于本库已确认的完整模式文件。

用户已明确采用的阅读约定可写入本库 Schema：检查标注、未标时一次提示并继续通读、梳理主题与逻辑、提炼底层方法、连接实操及问题索引。细节见 [阅读重点与方法提取](reading-focus.md)，不要在多个文件维护互相矛盾的提示规则。

`Schema.md` 只保留当前有效规则和必要的待决入口；详细历史在迭代记录，业务知识在知识页。创建后添加索引入口；修改前备份。Skill 开始执行时如存在 Schema，按需读取相关规则，其优先级高于本 Skill 的候选模板；用户当前指令优先。

## 怎样判断改进有效

针对发现的问题做最小验证，例如：用用户实际问题检索能否找到答案、点击结论能否追到原文、两份同义材料是否复用了同一概念页、用户认为重要的细节是否保留。不预设固定评分、节点数或迭代轮数。

如效果不好，回退或修订对应规则并记录原因；继续其他已授权工作，不叠加更多未经讨论的规则。案例完成时有新发现才简短报告“本次学到什么、改了什么、仍待观察什么”；无新发现则正常交付。

## Skill修改的版本记录

用户明确要求每次 Skill 修改用 Git 保留版本。规则变化实际写入本 Skill 后，按 [Git版本记录](version-control.md) 记录一轮完成修改的原因、文件、验证和版本标签；通过真实反馈调整后的新版本保留上版。知识页或单案例记录更新不自动成为 Skill 新版本。历史快照与正式版本的范围在 [版本历史](../VERSION_HISTORY.md) 中区分。
